# 拆活干活

## 一、开工前先写清“什么叫做完”

先读任务单，补齐六项。缺一项、而且会改变结果，就只问一个具体问题；不影响结果的，按常理补上，并在 `graph.md` 里写“假设：……”。

| 项 | 写什么 |
|---|---|
| 任务 | 一句话要做成什么 |
| 交付位置 | 产出和记录放哪个文件夹 |
| 做完的标准 | 看得见、能拿证据核的条件，一条一行 |
| 材料 | 要读的原文、已有的东西 |
| 能动的范围 | 哪些文件能改，哪些不能碰 |
| 上限 | 最多做几轮、多长时间 |

## 二、拆成节点

- 一个节点 = 一个输入、一个输出、一个检查。
- **按“这一步要读什么”来拆**，不按文件夹拆。
- 节点宁少勿多。三个能做完就不拆八个。
- 只有后一步要用前一步的产出，才排先后；互不依赖的可以同时做。
- 两种节点：
  - **程序节点**：有唯一正确答案的（数数、排序、去重、比对、格式转换）——写个小脚本做，不靠 AI 猜。
  - **判断节点**：要写、要看、要判断的——AI 来做。
- 把节点表写进交付位置的 `graph.md`（格式见文末）。

## 三、只在有风险的地方设关卡

关卡只放四处，其余只做轻检查（文件在、格式对、不为空）：

1. 对外发出去（发消息、发帖、发给客户）——**一律先问主人**；
2. 改正在运行的设置或服务；
3. 事实和引文（数字、日期、人名、原话）——要和原文逐条对上；
4. 花钱——**一律先问主人**。

过关卡要有证据，顺序固定：先程序检查 → 再看做的人的报告 → 最后才是判断。

## 四、干和查

1. 挑出输入已经齐的节点，做；
2. 每做完一个，按它的检查查一遍，结果写进 `checks.md`：

   ```
   | 节点 | 要求 | 结论 | 证据 |
   |---|---|---|---|
   | 整理清单 | 每条待办都有负责人 | 通过 | 清单.md 共 8 条，8 条有负责人 |
   ```
   结论只有 **通过 / 不通过 / 未定**；没证据就写“缺证据”，不能装通过。
3. 不过：**只退回那一个节点**，附上原因，最多重做 3 次；第 3 次还不过就停下，写成卡点交回。
4. 全部通过后，对照“做完的标准”整体再查一遍。
5. **绝不为了通过而降低标准。**

## 五、进度记录：progress.md

每做完一段就更新，固定五栏，让别的 AI 随时能接手：

```
## 状态    已完成：… / 进行中：… / 卡住：…（原因）
## 产出    每个产出的位置
## 决定    改了什么、为什么
## 待办    失败、疑问、卡点
## 下一步  下一个该做的节点
```

接手的人先读 `graph.md` 和 `progress.md`，从“下一步”接着做，不从头来。

## 六、交付

交：产出 + `graph.md` + `checks.md` + `progress.md`，再在交付文件夹里写一份 `说明.md`：
- 做成了什么、查了什么、还有什么没做完；
- 只报实际量到的（用了多久、做了几轮），不推测“省了多少”；
- 要主人决定的事，单独列出来。

做完建议换一个没参与的 AI 来查（见技能 `maker-checker`）。

## 附：graph.md 模板

```markdown
# <任务名>
- 任务：
- 交付位置：
- 做完的标准：1. … 2. …
- 材料：
- 能动的范围：
- 上限：

## 节点
| 编号 | 名称 | 种类（程序/判断） | 输入 | 输出 | 检查 |
|---|---|---|---|---|---|

## 先后
N1 → N2；可同时做的：…

## 假设
## 改动记录
```
